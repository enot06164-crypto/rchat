# Протокол rchat (v1)

Документ описывает обмен клиента и сервера: кадры, рукопожатие, методы,
синхронизацию, версионирование и правила эволюции. Источник истины по типам —
protobuf-схема в `crates/rchat-proto/proto/rchat/v1/`; здесь — семантика,
которую схема не выражает, и ключевые инварианты. Реализация конверта и
лимитов — `crates/rchat-proto/src/lib.rs`.

## 1. Транспорт и кадры

- Один WebSocket-канал на устройство; обмен — **бинарные кадры**, в каждом
  кадре ровно один protobuf-конверт `Envelope`:

  ```proto
  message Envelope {
    uint64 request_id = 1;
    oneof body {
      ClientHello client_hello = 2;
      ServerHello server_hello = 3;
      Request request = 4;
      Response response = 5;
      Push push = 6;
      Error error = 7;      // ошибка уровня соединения (без request_id)
    }
  }
  ```

- `request_id` > 0 связывает `Request` и `Response`. Для hello и push — 0.
- Битую или неизвестную ветвь `oneof` декодер превращает в `None`; это
  трактуется как неподдерживаемая операция/событие, а не как падение.
- Сервер отвечает на ping WebSocket; клиент шлёт собственный heartbeat.
  Отсутствие кадров дольше тайм-аута простоя (по умолчанию 150 с) —
  разрыв соединения.

Лимиты по умолчанию (значения из `rchat-proto::limits`, сервер может
уменьшать; фактические — в `ServerHello`):

| Лимит | По умолчанию | Жёсткий максимум |
| --- | --- | --- |
| Размер кадра (`max_frame_bytes`) | 256 КиБ | 1 МиБ |
| Содержимое сообщения (`max_message_bytes`) | 64 КиБ | — |
| Событий в странице синхронизации | 200 | 500 |
| Сообщений в странице истории | 50 | 100 |

Строки: username 3–32, display name 1–64, имя устройства ≤ 64, пароль
8–256, `client_message_id` ≤ 64.

## 2. Рукопожатие и сессии

1. Клиент отправляет `ClientHello` (версии major/minor, `capabilities`,
   `required_capabilities`, свой `max_frame_bytes`, имя и версия клиента).
   Ожидание `ClientHello` — не дольше 10 с, иначе соединение закрывается.
2. Сервер отвечает `ServerHello`: согласованные версии (major совпадает,
   minor — минимум из двух), пересечение capabilities, фактические лимиты,
   `sync_retention_seconds`, `e2e_protocol` (`olm.v1` или пусто) и имя сервера.
   Несовместимость (`PROTOCOL_VERSION_MISMATCH`, `UNSUPPORTED_CAPABILITY`) —
   фатальная ошибка соединения.
3. Аутентификация: `register`, `login` или `resume` (по сохранённому
   токену). До неё состояние — *unauthenticated*; состояние соединения
   клиента отражает фазу (`Connecting/Reconnecting/Unauthenticated/Connected`).
4. Токен сессии сервер выдаёт при регистрации/входе/возобновлении и хранит
   у клиента в `SecretStore`; срок жизни по умолчанию 30 дней. Сессия
   привязана к устройству (`device_id`): повторный вход с тем же `device_id`
   безопасно резюмирует ту же сущность, отозванное устройство запрещено к
   входу.
5. `logout` отзывает серверную сессию; локальный токен удаляется.

### Возможности (capabilities)

`receipts`, `presence`, `edit`, `delete`, `multi_device`, `history`,
`snapshot`, `e2e.olm.v1`, `groups`. Клиент объявляет требуемые возможности в
`required_capabilities`; сервер обязан поддержать их все, иначе отклоняет
соединение. Незнакомые дополнительные возможности игнорируются.

### Аутентификационные методы

| Метод | Запрос → ответ | Примечания |
| --- | --- | --- |
| `register` | `RegisterRequest` → `RegisterResponse` | Создаёт пользователя и первое устройство одной транзакцией; возвращает `user_id`, токен, устройство. |
| `login` | `LoginRequest` → `LoginResponse` | Если `device_id` неизвестен — создаёт устройство; если известен — ключи должны совпадать (`DEVICE_CONFLICT`). |
| `resume` | `ResumeRequest` → `ResumeResponse` | Восстановление сессии по непрозрачному токену. |
| `logout` | `LogoutRequest` → `LogoutResponse` | Отзыв текущей сессии. |
| `get_me` | `GetMeRequest` → `GetMeResponse` | Профиль и устройство текущей сессии. |

Регистрация/вход передают `DeviceInfo` (id, имя, платформа, ключи,
`e2e_version`), партию одноразовых prekey и резервный ключ. Устройство без
ключей (`e2e_version = 0`) допустимо, но в E2E-чатах участвовать не сможет.

## 3. Устройства и ключи

| Метод | Назначение |
| --- | --- |
| `upload_keys` | Дополнить пул одноразовых prekey и/или обновить резервный. |
| `get_device_bundles` | Пакеты для установления Olm-сессии: `DeviceKeys` + один выделенный prekey (одноразовый, иначе резервный); одноразовый выделяется «не более одного раза». |
| `get_devices` | Устройства указанных пользователей без выделения prekey (обновление кеша перед E2E-отправкой). |
| `list_devices` | Все (кроме отозванных) устройства своего аккаунта. |
| `revoke_device` | Отзыв устройства: его сессии разрываются, повторный вход запрещён. |

Отзыв устройства рассылается всем затронутым устройствам событием журнала
`DeviceChangedEvent(change = REVOKED)`; клиент удаляет Olm-сессии с
отозванным устройством.

## 4. Чаты

- `chat.kind` — `CHAT_KIND_DIRECT` или `CHAT_KIND_GROUP`.
- `chat.e2e_mode` фиксируется при создании: `E2E_MODE_OLM_V1` или
  `E2E_MODE_NONE_DEV` (явный режим разработки; сервер обязан быть запущен с
  `--allow-dev-plaintext-chats`, иначе `FORBIDDEN`). Переход E2E → plaintext
  запрещён.
- `create_direct_chat(peer_username, e2e_mode)` идемпотентен по паре
  участников: повторный вызов возвращает существующий чат.
- `list_chats` возвращает чаты с участниками и `last_server_id`
  (для отметки прочтения «до последнего»).

### Групповые чаты

Методы (40–44):

| Метод | Кто может | Смысл |
| --- | --- | --- |
| `create_group_chat(name, member_usernames[], e2e_mode)` | любой | Создаёт группу; создатель — владелец; приглашённые становятся участниками сразу. |
| `invite_to_chat(chat_id, usernames[])` | любой участник | Немедленное членство; повторное приглашение уже состоящего участника идемпотентно. |
| `leave_chat(chat_id)` | участник | Выход. Если выходит владелец, владение переходит участнику с самым ранним `joined_at_ms` (при равенстве — меньший `user_id`); пустая группа не удаляется. |
| `remove_chat_member(chat_id, user_id)` | только владелец | Исключение участника; владельца исключить нельзя (для владельца — `leave_chat`). |
| `rename_chat(chat_id, name)` | только владелец | Новое имя группы (1..=64 символов). |

`ChatMember.role` — `CHAT_MEMBER_ROLE_MEMBER` или `CHAT_MEMBER_ROLE_OWNER`
(в группе ровно один владелец; в личных чатах роль не заполняется).
`Chat.name` — имя группы; в личных чатах пусто.

Изменение состава рассылается всем, включая исключённых, событием
`ChatUpdatedEvent`: устройство, потерявшее членство, обязано увидеть
изменение, чтобы не отправлять сообщения, которые сервер отклонит, и чтобы
локальная история не смешивалась с новыми сообщениями. Новые сообщения
исключённым не адресуются и в их журнал не попадают.

Видимость устройств привязана к общим чатам: `get_devices` /
`get_device_bundles` возвращают устройства только тех пользователей, с
которыми у запрашивающего есть общий (не удалённый из состава) чат. После
исключения участники перестают видеть устройства друг друга, пока не
окажутся в общем чате снова.

## 5. Сообщения

### Отправка

`SendMessageRequest{chat_id, client_message_id, content_kind, reply_to_server_id,
recipients[], plaintext_dev}`.

- `client_message_id` — ключ идемпотентности (клиентский `local_id`).
  Повторная отправка с тем же ключом **в том же чате** возвращает результат
  первой, не создавая дубликат; повтор безопасен при реконнекте и после
  ответа, потерянного в сети.
- `recipients` — зашифрованные копии для каждого устройства получателей
  (кроме устройства отправителя), включая другие устройства самого автора.
  Для личного E2E-чата сервер проверяет покрытие всех неотозванных
  E2E-устройств участников; при нехватке — `E2E_KEYS_MISSING`, клиент
  пересобирает запрос со свежими бандлами.
- `plaintext_dev` допустим **только** в `E2E_MODE_NONE_DEV`; в E2E-чате
  отклоняется. В E2E-чате открытый текст не покидает клиент.
- **Групповой E2E-чат** (`CHAT_KIND_GROUP` + `E2E_MODE_OLM_V1`): содержимое —
  общий `group_ciphertext` (Megolm), а `recipients` несут только ключ
  сессии (`payload_kind = GROUP_KEY`) тем устройствам участников, у которых
  его ещё нет. Полное покрытие не требуется: участник без E2E-устройств
  получает ключ позже, при следующем устройстве/входе, зато начинает
  читать лишь с этого момента (более ранние сообщения ему недоступны).
  Пустой список `recipients` при непустом `group_ciphertext` допустим.
- `group_ciphertext`/`group_session_id` запрещены в личных и dev-чатах; в
  группе `group_ciphertext` обязателен, а копии `GROUP_KEY` разрешены только
  для E2E-устройств текущих участников.

### Поля `Message`

`server_id` (назначает сервер), `chat_id`, `sender_user_id`,
`sender_device_id`, `client_message_id`, `content_kind` (`text`),
`reply_to_server_id`, `created_at_ms`, `edited_at_ms`, `deleted_at_ms`,
`ciphertext` (копия именно для запрашивающего устройства),
`e2e_version`, `plaintext_dev` (только dev-чаты), `sender_curve25519`,
`olm_type` (`NORMAL`/`PREKEY`), `group_ciphertext`, `group_session_id`,
`recipient_payload_kind`.

Если для запрашивающего устройства копии нет (например, оно
зарегистрировано позже отправки), `ciphertext` пуст — история отдаётся, но
это сообщение устройство прочитать не сможет. Для группового E2E-сообщения
отсутствие персональной копии не делает его нечитаемым: содержимое — общий
`group_ciphertext`, поэтому в таком представлении `e2e_version` остаётся
`E2E_VERSION_OLM_V1` (ключ сессии был выдан ранее), а устройство без ключа
деградирует до «сообщение без текста».

### История

`get_history(chat_id, before_server_id, limit)` — страница новых вниз
(строго старее `before_server_id`), `has_more` для пагинации. Клиент
параллельно накапливает локальный кеш; `history --from-server` в CLI читает
сервер.

### Правка и удаление

- `edit_message(server_id, content_kind, recipients[], plaintext_dev,
  group_ciphertext, group_session_id)` —
  только автор (любое его устройство). Новые копии шифруются по тем же
  правилам покрытия; сервер заменяет ciphertext-ы, выставляет
  `edited_at_ms` и **переводит авторство на устройство-редактор**
  (`sender_device_id` и identity-ключ), чтобы получатели корректно
  расшифровали правку с другого устройства автора. В групповом E2E-чате
  правка заменяет и общий `group_ciphertext` (сессия может быть новой —
  например, после ротации) вместе с `group_session_id`.
- `delete_message(server_id)` — политика одна: «удалить для всех»
  (tombstone). Сервер стирает ciphertext-ы и dev-plaintext, выставляет
  `deleted_at_ms`; событие приходит без содержимого. Повторное удаление
  идемпотентно. «Удалить для себя» не поддерживается.
- Оба действия попадают в журнал синхронизации каждого устройства; клиент,
  пропустивший их в офлайне, применяет события при следующем подключении.

### Квитанции (receipts)

`mark_receipt(chat_id, up_to_server_id, read)`:

- `read = false` — delivered: устройство применило сообщения до
  `up_to_server_id`; клиент отправляет автоматически при применении
  входящих;
- `read = true` — пользователь прочитал (в CLI — команда `read`).

Квитанции **монотонны** (повторные и меньшие значения не откатывают
прогресс) и отклоняются «в будущее» (значение больше текущего
`last_server_id` чата — ошибка). Прогресс рассылается всем участникам и
догружается через журнал: устройство, пропустившее квитанцию, получит её
событием.

## 6. Синхронизация

Журнал событий ведётся **на каждое устройство** отдельно; `seq` непрерывен.

- **Push.** Сервер присылает `Push{sync_event}` при записи события в журнал
  устройства; `kind_hint` повторяет номер поля полезной нагрузки и виден
  даже для неизвестных клиенту типов событий.
- **Pull.** `sync(after_seq, limit)` возвращает
  `SyncEventsResponse{from_seq, events[], up_to_seq, resync_required}`.
  `up_to_seq` — максимальный seq журнала на момент ответа.
- **Курсор клиента** — последний надёжно применённый seq. Правила:
  - событие применяется, только если `seq == cursor + 1`; иначе включается
    pull-синхронизация (разрыв последовательности);
  - повторная доставка (`seq <= cursor`) безопасно игнорируется;
  - пачка мутаций и продвижение курсора применяются **одной транзакцией**
    хранилища: сбой не продвигает курсор, состояние не мутируется;
  - неизвестные события пропускаются **с продвижением курсора** — это
    правило совместимости, а не ошибка.

Типы событий (`SyncEvent.payload`):

| `kind_hint` | Событие | Смысл |
| --- | --- | --- |
| 10 | `ChatCreatedEvent` | Появился чат (участники, режим E2E). |
| 11 | `MessageEvent` | Новое сообщение. |
| 12 | `MessageEditedEvent` | Правка (авторство — устройство-редактор). |
| 13 | `MessageDeletedEvent` | Tombstone без содержимого. |
| 14 | `ReceiptEvent` | Прогресс delivered/read участника. |
| 15 | `DeviceChangedEvent` | Устройство добавлено/отозвано. |
| 16 | `ChatUpdatedEvent` | Изменение состава/имени группы (в т.ч. для исключённых). |

- **Retention и resync.** События старше `sync_retention_seconds`
  (по умолчанию 7 суток) удаляются, но последние `sync_keep_min_events`
  (500) хранятся всегда. Если курсор устройства указывает на удалённый
  участок, сервер отвечает `resync_required = true`: клиент получает
  `snapshot` (чаты, собственные устройства, пользователи, `up_to_seq`),
  продолжает с `up_to_seq` и перезапрашивает историю через `get_history`.
- **Presence** — не в журнале: `Push{transient.presence}` — best-effort.
  При подключении устройство получает срез присутствия собеседников, при
  разрыве рассылается offline. После рестарта сервера состояние сбрасывается.

## 7. Ошибки

Ответ с ошибкой — `Response.result = Error{code, message, retryable}`;
ошибка уровня соединения — `Envelope.error`. `message` не содержит
внутренних деталей (SQL, стеков).

| Код | Когда |
| --- | --- |
| `INVALID_REQUEST`, `PAYLOAD_TOO_LARGE`, `LIMIT_EXCEEDED` | Невалидный запрос, превышение лимитов. |
| `UNSUPPORTED_METHOD`, `PROTOCOL_VERSION_MISMATCH`, `UNSUPPORTED_CAPABILITY` | Несовместимость/неизвестный метод. |
| `INVALID_CREDENTIALS`, `UNAUTHENTICATED`, `SESSION_EXPIRED`, `SESSION_REVOKED` | Проблемы входа/сессии. |
| `USERNAME_TAKEN`, `USERNAME_INVALID`, `DEVICE_CONFLICT` | Конфликты данных устройства/аккаунта. |
| `FORBIDDEN`, `NOT_FOUND`, `CONFLICT` | Доступ и адресация. |
| `RATE_LIMITED` | Превышен лимит (см. ниже); `retryable = true`. |
| `E2E_REQUIRED`, `E2E_KEYS_MISSING` | Нельзя отправить открытый текст в E2E-чат; неполное покрытие устройств. |
| `RESYNC_REQUIRED` | Курсор устарел; нужен snapshot. |
| `INTERNAL` | Внутренняя ошибка без деталей. |

Rate-limit (в памяти одного процесса, значения по умолчанию): регистрации —
10/час на сетевой адрес, попытки входа — 10 за 5 минут на username, отправка
сообщений — 120/минуту на пользователя.

## 8. Версионирование и эволюция схемы

- `PROTOCOL_MAJOR = 1`, `PROTOCOL_MINOR = 0`; major несовместим, minor
  согласуется как минимум из двух. Возможности объявляются отдельно от
  версий.
- Правила эволюции protobuf-схемы (продублированы в `common.proto`):
  - номера полей и значения enum **не переиспользуются**, удалённые —
    резервируются через `reserved`;
  - новые поля добавляются только с новыми номерами; неизвестные поля
    игнорируются декодером;
  - неизвестные значения enum сохраняются как raw int и обрабатываются
    безопасно;
  - неизвестная ветвь `oneof` при декодировании становится `None` —
    вызывающий код трактует это как неподдерживаемую операцию/событие;
  - неизвестное событие синхронизации пропускается с продвижением курсора.
- Распределение номеров методов `Request`/`Response`: 1–9 — аутентификация,
  сессии, устройства и ключи; 10–19 — чаты и сообщения; 20–29 —
  синхронизация; 30–39 — прочие операции; 40–49 — групповые чаты;
  100 — общая ошибка; ≥ 200 — зарезервировано.
- E2E-протокол версионируется отдельно: `e2e_version = 1` / строка
  `olm.v1` (`E2E_VERSION_OLM_V1`, `E2E_PROTOCOL_OLM_V1`).

## 9. Инварианты клиента, опирающиеся на протокол

- Ответ на запрос всегда сопоставляется по `request_id`; опоздавшие и
  дублирующиеся ответы игнорируются.
- Повторные доставки push/событий и повторные ответы сервера не создают
  дубликатов в локальном хранилище (дедупликация по `server_id` и по ключу
  идемпотентности).
- Нестабильность сети (обрыв, задержка, повтор кадра, битый кадр) не
  приводит к потере или дублированию сообщений: outbox повторяет отправку с
  тем же `client_message_id`, а поток битых кадров (более 10 за соединение)
  закрывает соединение и запускает переподключение с чистым потоком.
- Ключ групповой megolm-сессии выдаётся устройству не более одного раза:
  клиент запоминает состоявшиеся выдачи (`group_key_shares`) и при
  ротации сессии (исключение/выход участника, отзыв устройства, необратимый
  сбой отправки) очищает их и рассылает ключ заново.
- Выбытие участника закрывает ему чтение новых сообщений не только
  доставкой: сессия ротируется при изменении состава — как в ответе на
  запрос, так и в событии журнала, и при пересборке состояния из снимка
  (например, после перезапуска CLI).
