# Архитектура rchat

Документ фиксирует принятые решения по структуре workspace, направлению
зависимостей и ключевым механизмам клиента и сервера. Полный план (README,
`docs/protocol.md`, `docs/threat-model.md`, `docs/extension-guide.md`,
`docs/testing.md`) завершается на финальном этапе; здесь описана уже
реализованная часть и её обоснование.

## 1. Обзор

rchat — клиент-серверный мессенджер на Rust. Сервер хранит аккаунты,
устройства, чаты и сообщения; клиент — локальный кеш, очередь отправки и
(начиная с этапа 6) E2E-состояние. Первый клиент — CLI; ядро клиента не
знает ни о транспорте, ни о хранилище, ни о CLI, поэтому позже к нему
подключаются другие интерфейсы и транспорты.

## 2. Крейты и направление зависимостей

| Крейт | Назначение | Ключевые зависимости |
| --- | --- | --- |
| `rchat-proto` | protobuf-схема, конверт (`Envelope`), лимиты, версии | `prost`, `thiserror`, `getrandom` |
| `rchat-core` | доменная логика клиента: сессии, синхронизация, outbox, E2E-контракты, события UI | `rchat-proto`, `tokio` (sync/time), `async-trait`, `prost`, `thiserror`, `tracing`, `getrandom` |
| `rchat-server` | сервисный слой сервера и контракт хранилища `Repo` | `rchat-proto`, `tokio`, `async-trait`, `argon2` |
| `rchat-server-storage-sqlite` | SQLite-реализация `Repo`, сетевой слой (TLS+WebSocket) и бинарник `rchat-server` | `rchat-server`, `rusqlite`, `tokio-tungstenite`, `rustls`, `rcgen` |
| `rchat-transport-ws` | WebSocket + TLS транспорт клиента | `rchat-core`, `tokio-tungstenite`, `rustls`, `rustls-native-certs`, `sha2` |
| `rchat-client-storage-sqlite` | SQLite-хранилище клиента (`Storage`, `CryptoStateStore`) и шифрованное файловое хранилище секретов | `rchat-core`, `rusqlite`, `chacha20poly1305`, `getrandom`, `zeroize` |
| `rchat-crypto-provider` | E2E-провайдер (vodozemac/Olm) | `rchat-core`, `vodozemac` |
| `rchat-testkit` | сценарии и in-memory реализации для тестов | `rchat-core`, `rchat-server` |
| `rchat-e2e-tests` | кросс-крейтовые end-to-end сценарии | testkit, транспорты, хранилища |
| `rchat-cli` | composition root CLI: собирает ядро с конкретными адаптерами | `rchat-core`, `rchat-transport-ws`, `rchat-client-storage-sqlite`, `clap`, `rpassword`, `directories` |

Направление зависимостей — только «вниз»: адаптеры знают о ядре, ядро об
адаптерах — нет. Правило закреплено тестом
`crates/rchat-core/tests/dependency_rules.rs`: манифест ядра проверяется на
запрещённые крейты (транспорт, SQL/СУБД, HTTP-фреймворки, CLI-парсеры,
криптографические библиотеки, реализации хранилищ секретов, `directories` и
`rpassword`) и на осознанно минимальный белый список.

## 3. Протокол

- Транспорт — один WebSocket-канал на устройство; обмен — бинарные кадры
  `Envelope{request_id, oneof}` с ограничением размера 1 МиБ.
- Неизвестный метод → `UnsupportedMethod`; неизвестные значения enum
  сохраняются как есть; неизвестные события синхронизации пропускаются с
  продвижением курсора (см. §5) — это правило совместимости заложено в
  парсинг конверта и применяется ядром.
- Версии: `PROTOCOL_VERSION` и `E2E_VERSION` живут в `rchat-proto`;
  возможности клиента передаются в `ClientHello` (`required_capabilities`),
  сервер отвечает `ServerHello`.

## 4. Сервер

- **Один экземпляр.** Реестр соединений и presence живут в памяти процесса;
  устойчивое состояние — только SQLite. Для нескольких узлов потребуются:
  общий репозиторий (вместо локального файла), адресация устройств и
  доставка между узлами (внешняя шина/pub-sub), sticky-маршрутизация
  соединений, согласованный счётчик `server_id` (UUID/снежинки) и общий
  rate-limit. Эти интерфейсы сознательно не выделены «на будущее».
- **Хранилище.** `Repo` — контракт сервисного слоя; SQLite-реализация
  держит одно соединение, сериализует доступ мьютексом и выполняет работу в
  `spawn_blocking`. Транзакционные границы совпадают с бизнес-операциями
  (регистрация, вставка сообщения вместе с получателями и событиями,
  выдача предключей, применение receipts).
- **Синхронизация.** Журнал событий ведётся на каждое устройство,
  `seq` непрерывен. Сервер хранит минимально доступный `seq` и при
  устаревшем курсоре требует resync: клиент получает snapshot (чаты) и
  перезапрашивает историю.
- **Идемпотентность.** `client_message_id` уникален в рамках чата: повторная
  отправка возвращает то же `server_id`, не создавая дубликат.
- **Безопасность.** Пароли — Argon2id; TLS обязателен вне явно локального
  тестирования (`--plaintext-insecure` допускается только для loopback);
  чаты `E2E_MODE_NONE_DEV` включаются только флагом
  `--allow-dev-plaintext-chats`.
- **Dev-режим TLS.** По умолчанию сервер генерирует самоподписанный
  сертификат и печатает SHA-256 отпечаток в лог — клиент подключается с
  `--tls-fingerprint`.

## 5. Клиент (ядро)

- **Актор соединения.** Один последовательный владелец транспорта:
  выполняет `ClientHello`/`ServerHello`, `Resume` по сохранённому токену,
  разрешает ответ на `request_id`, а push-конверты (presence, события
  синхронизации, receipts) обрабатывает вне цикла запросов. Реконнект — с
  экспоненциальной задержкой и джиттером.
- **Outbox.** Ключ идемпотентности — `local_id` сообщения. Состояния
  `Pending/Sending/Sent/Failed`; при разрыве соединения `Sending`
  возвращается в `Pending`. Повторы с backoff; ошибка `E2E_KEYS_MISSING`
  приводит к пересборке бандла свежими предключами. Подтверждение
  (`apply_send_ack`) атомарно проставляет `server_id`, статус `Sent`,
  удаляет строку очереди и обновляет чат.
- **Применение синхронизации.** Push-событие применяется, только если
  `seq == cursor + 1`; разрыв последовательности переводит клиента на
  pull-sync. Пачка мутаций и продвижение курсора применяются одной
  транзакцией: сбой не продвигает курсор. Неизвестные события
  пропускаются, но курсор продвигается.
- **События UI.** Широковещательный канал; подписчик может отстать
  (`Lagged`) — состояние всегда можно перечитать из хранилища, события не
  являются источником истины.

## 6. Хранилище клиента (SQLite)

Таблицы: `schema_migrations`, `account`, `users`, `devices`, `chats`,
`chat_members`, `messages`, `outbox`, `sync_state`, `receipts`,
`crypto_state`. Версия схемы поднимается идемпотентными миграциями; каждая
миграция — отдельная транзакция.

Ключевые решения:

- `local_id` — первичный ключ сообщений; `server_id` уникален (NULL до
  подтверждения). Собственные сообщения создаются с локальным id, принятые —
  с `s:<server_id>`, что делает повторную доставку идемпотентной
  (`ON CONFLICT DO NOTHING`).
- Подтверждение отправки удаляет «эхо»-копию, если событие о собственном
  сообщении успело прийти раньше ответа на запрос; повторное подтверждение
  идемпотентно.
- Receipts и отзыв устройств монотонны (`MAX`/`COALESCE`), кеш устройств не
  затирает уже известные публичные ключи пустыми значениями.
- Курсор синхронизации только растёт; `clear_all` (logout --wipe) очищает
  все таблицы и сбрасывает курсор.

## 7. Транспорт и доверие TLS

- `ws://` — только для явного локального тестирования; вне loopback
  требуется `wss://`.
- Режимы доверия (`TlsTrust`): системные корни (боевой), пиннинг SHA-256
  отпечатка листового сертификата (локальная разработка, самоподписанные
  сертификаты), `Insecure` (полное отключение проверки — только по явному
  флагу для локальных сценариев). Пиннинг проверяет и подпись рукопожатия:
  отпечаток фиксирует конкретный сертификат, дальше проверяется владение
  ключом.
- В `recv` совмещены чтение кадров, ответы на ping сервера и собственный
  heartbeat; отсутствие кадров дольше `read_timeout` считается потерей
  соединения. Размер входящих сообщений ограничен лимитом протокола.

## 8. Секреты

Платформенные хранилища (Secret Service/Keychain) не входят в зависимости
первого релиза, поэтому применяется резервный способ —
`EncryptedFileSecretStore`:

- секреты (токен сессии, ключ шифрования pickles, id устройства) лежат в
  одном файле, зашифрованном XChaCha20-Poly1305 (AEAD со случайным nonce на
  каждую запись);
- ключ шифрования хранится **в отдельном файле** с правами `0600`, каталог —
  `0700`; ключ и значения не выводятся в `Debug` и не логируются;
- запись атомарная (временный файл → `fsync` → `rename`), что исключает
  частично записанные секреты.

Ограничение честно фиксируется: при компрометации каталога пользователя
секреты скомпрометированы (ключ лежит рядом, защищён только правами ФС), а
на не-Unix платформах права не выставляются. Хранилище однопроцессное.

## 9. Локальный запуск

```bash
# Сервер: dev-TLS (самоподписанный), отпечаток печатается в лог.
cargo run -p rchat-server-storage-sqlite --bin rchat-server -- \
    --db rchat.sqlite3 --listen 127.0.0.1:8443

# Клиент: пиннинг отпечатка из лога сервера.
cargo run -p rchat-cli -- --server wss://localhost:8443 \
    --data-dir /tmp/alice --tls-fingerprint <aa:bb:...> register alice

# Второй клиент.
cargo run -p rchat-cli -- --server wss://localhost:8443 \
    --data-dir /tmp/bob --tls-fingerprint <aa:bb:...> register bob

# Чат, отправка, синхронизация, живой режим.
cargo run -p rchat-cli -- --data-dir /tmp/alice chat-create bob
cargo run -p rchat-cli -- --data-dir /tmp/alice send <chat_id> Привет
cargo run -p rchat-cli -- --data-dir /tmp/bob sync
cargo run -p rchat-cli -- --data-dir /tmp/bob watch
```

Для локальных экспериментов без TLS сервер запускается с
`--plaintext-insecure --allow-dev-plaintext-chats`, клиент — без
`--tls-fingerprint` и с `ws://` (только loopback).

## 10. Известные ограничения первого релиза

- server presence и реестр соединений — в памяти одного процесса (§4);
- E2E включается на этапе 6 (vodozemac/Olm): до этого доступны только
  `E2E_MODE_NONE_DEV`-чаты под явным флагом сервера;
- серверу видны метаданные: участники, время, размер и факт активности;
- каталог данных клиента (кроме файла секретов) не шифруется — SQLite-кеш
  сообщений защищён только правами файловой системы;
- `TlsTrust::Insecure` и `ws://` существуют только для локальных сценариев и
  запрещены к использованию вне loopback.
