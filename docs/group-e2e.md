# Групповой E2E (Megolm) — отдельная спецификация

Документ фиксирует дизайн группового сквозного шифрования rchat: модель
участия, криптографическую схему, правила выдачи и ротации ключей,
инварианты и их проверку. Он дополняет `docs/protocol.md` (протокол),
`docs/architecture.md` §7 (реализация) и `docs/threat-model.md`
(гарантии и остаточные риски).

Техническое задание `rchat_technical_spec_v2.md` (§ «Групповое E2E не входит
в первый релиз») требует для групп отдельно выбранный и спроектированный
групповой протокол. Выбор сделан в пользу **Megolm** из уже используемой
библиотеки vodozemac 0.11.1; обоснование и сравнение с MLS — ниже.

## 1. Область

Входит:

- групповые чаты с немедленным членством (приглашение = участник);
- роли: владелец и участник (исключение и переименование — только владелец);
- E2E-режим `E2E_MODE_OLM_V1` для групп на Megolm;
- dev-режим `E2E_MODE_NONE_DEV` для групп (только с явным флагом сервера);
- ротация исходящей сессии при смене состава, отзыве устройства и
  необратимом сбое отправки.

Не входит:

- MLS и его свойства (эпохи, криптографическая аутентификация членства,
  пост-компромиссная безопасность группы);
- доставка истории новым участникам (общего «журнала ключей» нет);
- подтверждаемые приглашения, заявки на вступление, публичные группы;
- вложения, реакции, треды (содержимое — только текст, как и в v1).

## 2. Выбор протокола

| Критерий | Megolm (выбран) | MLS (OpenMLS) |
| --- | --- | --- |
| Библиотека | уже есть (vodozemac, тот же крейт, что Olm) | новый крейт + собственный протокольный слой (welcome/commit) |
| Совместимость с текущей моделью | ключ сессии — такой же непрозрачный payload для сервера, как Olm-копия | требуется отдельная доставка welcome/commit и «эпох» |
| Свойства | групповой ratchet, forward secrecy внутри сессии | пост-компромиссная безопасность, аутентификация состава |
| Объём изменений в v1-протоколе | поля `group_ciphertext`/`group_session_id` + `payload_kind` | новый набор методов синхронизации состава |

В v1 групповые чаты закрываются Megolm'ом: новых криптографических
примитивов не появляется, сервер по-прежнему не видит содержимого, а
контракты «ядро не зависит от криптобиблиотеки» сохраняются. MLS остаётся
осознанным будущим шагом (со своей спецификацией и миграцией).

## 3. Модель участия

- Создатель группы — владелец; приглашённые (по логину) становятся
  участниками немедленно.
- Приглашать может любой участник; повторное приглашение состоящего
  участника идемпотентно.
- Исключать участников и переименовывать группу может только владелец;
  владельца исключить нельзя (для владельца — выход).
- При выходе владельца владение переходит участнику с самым ранним
  `joined_at_ms` (при равенстве — меньший `user_id`).
- Пустая группа не удаляется: последний участник может выйти, группа
  остаётся без участников.
- Изменение состава рассылается всем участникам, **включая исключённых**
  (событие `ChatUpdatedEvent`, `kind_hint = 16`), чтобы выбывшее устройство
  знало о потере членства и не пыталось отправлять.
- Новые сообщения адресуются только текущему составу: исключённый не
  получает ни события, ни копии ключа; сервер отклоняет его отправку.

## 4. Криптографическая схема

**Сессии.** Исходящая мегалом-сессия — своя у каждого устройства в каждом
чате (`megolm_out:<chat_id>`). Входящие сессии хранятся по
`megolm_in:<session_id>`, привязка к чату — внутри записи: ключ,
полученный в одном чате, не действует в другом. Session id — base64 из
vodozemac.

**Содержимое.** `Message.group_ciphertext` — результат
`GroupSession::encrypt`; общий для всех. `Message.group_session_id` —
идентификатор сессии.

**Выдача ключа.** Ключ сессии (`GroupSession::session_key`) упаковывается в
непрозрачный для ядра конверт:

```
MAGIC "RMGK" | version = 1 | u16 BE len(chat_id) | chat_id | u16 BE len(key) | key
```

и шифруется Olm-сессией конкретного устройства. В запросе это
`RecipientPayload{ payload_kind = GROUP_KEY, ciphertext, olm_type,
sender_curve25519 }`. Для устройств без установленной Olm-сессии
запрашиваются prekey-бандлы; остальным ключ уходит обычным Olm-сообщением.

**Порядок «ключ до шифрования».** Ключ берётся **до** шифрования текущего
сообщения, поэтому выданный ключ соответствует ратчету именно этого
сообщения: получатель читает сообщение, вместе с которым пришёл ключ, и все
последующие, но не предыдущие. Обновление ключа «задним числом»
невозможно — согласованная история отсутствует by design.

**Учёт выдач.** Клиент хранит `group_key_shares(chat_id, session_id,
device_id, shared_at_ms)`. Запись создаётся после того, как запрос отправки
(или правки) поставлен в outbox, — до подтверждения сервера, чтобы
пересборка запроса не дублировала рассылку. Повторная отправка в ту же
сессию не несёт ключей вовсе (`recipients` может быть пустым); приглашённый
получает ключ со следующим сообщением, а не полным «сбросом» рассылки.

**Ротация.** Исходящая сессия ротируется, а записи выдач очищаются, при:

1. исключении участника или его выходе (`ChatUpdated`);
2. отзыве устройства участника (`DeviceChanged` = REVOKED);
3. необратимом провале отправки группового сообщения (outbox: постоянная
   ошибка — например, истёк лимит попыток при отвергнутом запросе).

Смена состава определяется сравнением с локально сохранённым составом
**до** его обновления — это работает и в ответе сервера, и в событии
журнала, и при пересборке состояния из снимка (после перезапуска CLI,
resync). Ротация гарантирует: выбывший не читает ни одного нового
сообщения, даже если получит `group_ciphertext` по стороннему каналу.

## 5. Приём

1. Если в сообщении непусты `group_ciphertext`/`group_session_id` — это
   групповое содержимое; проверка выполняется **до** режима `e2e_version`
   (сообщение с megolm-содержимым может прийти без персональной копии).
2. При `recipient_payload_kind = GROUP_KEY` и непустом `ciphertext` — импорт
   ключа (`apply_group_key`): проверяется привязка к `chat_id`, повторный
   импорт идемпотентен (ратчет не откатывается).
3. Расшифровка общего `group_ciphertext` входящей сессией этого
   `session_id`.
4. Любая неудача — «сообщение видно, текста нет» плюс событие
   `E2eDecryptFailed` (кроме сообщений собственного устройства-отправителя:
   своей исходящей сессии у него нет, его текст берётся из локальной
   записи). История и состояние при этом не теряются.

## 6. Протокол

- Методы 40–44: `create_group_chat`, `invite_to_chat`, `leave_chat`,
  `remove_chat_member`, `rename_chat`; ответы несут снимок `Chat`.
- `Chat.kind = CHAT_KIND_GROUP`, `Chat.name` — имя группы,
  `ChatMember.role` — роль.
- Полей содержимого два новых: `group_ciphertext`, `group_session_id`
  (`SendMessageRequest`, `EditMessageRequest`, `Message`), плюс
  `RecipientPayload.payload_kind`.
- Правка в группе заменяет общий `group_ciphertext` вместе с
  `group_session_id` (сессия может быть новой после ротации).
- Серверная валидация: в группе `group_ciphertext` обязателен, копии —
  только `GROUP_KEY` и только E2E-устройствам текущих участников; полное
  покрытие не требуется. В личных и dev-чатах групповые поля запрещены.
- Видимость устройств привязана к общим чатам: после исключения участники
  не видят устройств друг друга, пока снова не окажутся в общем чате.
- `e2e_version` представления сообщения остаётся `OLM_V1`, даже если
  персональной копии у устройства нет (ключ выдан ранее) — иначе клиент не
  попытался бы расшифровать содержимое.

## 7. Инварианты и их проверка

| Инвариант | Тест |
| --- | --- |
| Сервер не хранит открытый текст групп и не видит ключей | `group_chat.rs` (сервер), `group_e2e.rs`, `cli_smoke.rs` (SQL-проверки) |
| Ключ не дублируется при повторных отправках | `group_e2e.rs::group_e2e_lifecycle_with_rotation`, `group_e2e_multi_device` |
| Приглашённый не читает ранние сообщения | `group_e2e.rs::group_late_member_cannot_read_earlier_messages` |
| Исключение ротирует сессию; исключённый не читает новые | `group_e2e.rs::group_e2e_lifecycle_with_rotation`, `cli_smoke.rs::group_chat_lifecycle` |
| Ротация срабатывает и из снимка при входе | `cli_smoke.rs::group_chat_lifecycle` (каждая команда — новый процесс) |
| Ключ выдаётся каждому устройству участника (мультиустройство) | `group_e2e.rs::group_e2e_multi_device` |
| Ратчет продолжается в одной сессии | `rchat-crypto-provider::tests::group_session_ratchet_advances` |
| Ключ привязан к чату и не переносится | `rchat-crypto-provider::tests::group_key_is_bound_to_its_chat` |
| Роли, владение, передача при выходе, запрет исключения владельца | `group_chat.rs` (12 серверных сценариев) |
| Ротация при изменении состава сохраняется после перезапуска | `client_store.rs::migration_adds_member_roles_and_group_key_shares` (учёт выдач), `group_e2e.rs` |

## 8. Ограничения (честно)

- **Нет криптографической аутентификации состава**: членство назначает
  сервер; клиент принимает состав из подписанного снимка/событий TLS-сессии,
  но не может доказать, что владелец действительно добавил участника.
- **Нет пост-компромиссной безопасности группы**: компрометация
  мегалом-сессии раскрывает её сообщения (включая предыдущие той же
  сессии); ключ сессии лежит на устройствах участников до ротации.
- **История не пересылается**: ключ действует только «вперёд»;
  приглашённый видит текст с момента приглашения.
- **Выбывший сохраняет уже расшифрованное**: E2E не отзывает ранее
  полученный открытый текст.
- **Метаданные группы видны серверу**: состав, имена, роли, время,
  размеры, факты ротации (новая `group_session_id`).
- **Один мегалом-ратчет на устройство и чат**: параллельные сессии
  (несколько активных отправителей) — это разные сессии, что нормально, но
  «единого порядка» сообщений на всех нет; порядок задаёт сервер
  (`server_id`).
