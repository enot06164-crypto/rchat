# Гид по расширению

Документ описывает, как добавлять в rchat новые адаптеры, интерфейсы и
протокольные возможности, не нарушая зафиксированную архитектуру. Он
опирается на `docs/architecture.md` (структура) и `docs/protocol.md`
(протокол).

## 1. Общие правила

- **Направление зависимостей — только «вниз».** `rchat-core` не знает о
  транспорте, хранилище, криптопровайдере и UI: он работает через трейты.
  Правило закреплено тестом `crates/rchat-core/tests/dependency_rules.rs`.
  Если ядру понадобилась новая зависимость — сначала ответьте, почему это не
  адаптер; при необходимости обновите белый список в тесте осознанно.
- **Новый адаптер — новый крейт**, подключаемый в composition root
  (`rchat-cli/src/app.rs` и `rchat-ffi/src/config.rs` для клиента,
  `rchat-server-storage-sqlite` для серверного бинарника). Версии
  зависимостей задаются в workspace `[workspace.dependencies]`.
- **Тесты — вместе с расширением**, по слоям из `docs/testing.md`.
  Инструменты (TestServer, MockStorage, помехи транспорту) дают `rchat-testkit`.

## 2. Новый транспорт клиента

Контракт — `rchat_core::traits::{Transport, TransportFactory}`:

```rust
#[async_trait]
pub trait Transport: Send {
    async fn send(&mut self, frame: &[u8]) -> Result<(), TransportError>;
    async fn recv(&mut self) -> Result<Option<Vec<u8>>, TransportError>;
    async fn close(&mut self) -> Result<(), TransportError>;
}

#[async_trait]
pub trait TransportFactory: Send + Sync {
    async fn connect(&self) -> Result<Box<dyn Transport>, TransportError>;
}
```

Требования и типичные ошибки:

- Кадр — уже сериализованный `Envelope`; транспорт не разбирает содержимое.
- `Ok(None)` — корректное закрытие; любая ошибка — потеря соединения.
  Реконнект с backoff и повторные отправки outbox — забота ядра.
- `recv` должен быть **cancel-safe**: ядро опрашивает его в `select!` вместе
  с командами и таймерами. На транспортных обёртках (`tokio-tungstenite`)
  это уже так; при написании своей проверяйте документацию примитива.
- Политика доверия TLS (системные корни/пиннинг/`Insecure`) — часть
  адаптера, а не ядра. Образец — `rchat-transport-ws`.

Проверка: оберните фабрику в `rchat_testkit::MockTransportFactory` и
прогоните сценарии из `docs/testing.md` §5 (разрыв, задержка, дубли,
битые кадры) — они не зависят от конкретного транспорта.

## 3. Новое клиентское хранилище

Контракты — `Storage` + `CryptoStateStore` (вместе — `ClientStore`) и
отдельно `SecretStore` (`rchat_core::traits`). Ключевые требования, на
которые опирается ядро:

- `apply_sync_batch(ops, seq)` **атомарен**: мутации и курсор применяются
  одной транзакцией; при ошибке не меняется ничего, включая курсор;
- курсор синхронизации только растёт (`set_sync_cursor` — монотонно);
- вставка входящих сообщений идемпотентна по `server_id`; порядок выдачи —
  новые первыми (`list_messages`); подтверждение отправки переводит
  локальное сообщение в `Sent` и удаляет «эхо»-копию;
- receipts и отметки отозванных устройств монотонны (`MAX`/`COALESCE`);
  затирание известных ключей устройств пустыми значениями недопустимо;
- `clear_all` (logout `--wipe`) очищает всё и сбрасывает курсор.

`SecretStore` — синхронный (`get/set/delete`), обязан быть потокобезопасным,
писать атомарно и не логировать значения. Имена ключей — в
`rchat_core::traits::secret_keys`; идентификатор устройства хранится там же.

Семантика-образец — `rchat-client-storage-sqlite`; in-memory аналог для
тестов — `rchat_testkit::MockStorage` (в нём же `fail_next_batch()`).

## 4. Новый UI / приложение-клиент

Сборка клиента:

```rust
let client = ClientBuilder::new(config, transport, storage, secrets)
    .crypto_provider(provider)   // обязателен при e2e_enabled = true и наоборот
    .build()?;
client.start().await?;
let mut events = client.subscribe();       // UiEvent
```

- Команды API (`register/login`, `send_text`, `create_direct_chat`,
  `sync_now`, `mark_read`, `receipts`, `devices`…) асинхронны и сами ждут
  соединения там, где это осмысленно.
- `subscribe()` даёт широковещательный поток `UiEvent` (сообщения,
  изменения, presence, состояние outbox). Подписчик может отстать
  (`Lagged`) — источник истины всегда хранилище, событие лишь сигнал.
- `connection_state()` — текущая фаза соединения (watch-канал, значение
  сохраняется даже без подписчиков).
- Долгоживущий процесс — это цикл по событиям; one-shot команды не
  должны создавать собственных реконнектов.

Образец жизненного цикла — `rchat-cli/src/app.rs` (`watch`, `send --wait`,
`status`).

### 4.1. C-ABI/JSON (`rchat-ffi`)

`rchat-ffi` — второй composition root. Ядро остаётся свободным от JSON:
сериализация и C-ABI живут только в этом крейте.

- Новая команда: добавьте ветку в `src/commands.rs` (валидация полей,
  вызов метода `Client`, ответ через `json.rs`), опишите её в
  `docs/ffi.md` и покройте вызовом в `tests/ffi.rs`.
- Новое событие: добавьте вариант в `UiEvent` (ядро), ветку в
  `src/json.rs`, строку в таблицу событий `docs/ffi.md` и тест.
- Не добавляйте в ядро `serde`, `serde_json` или C-типы: FFI — адаптер,
  как CLI.
- C-ABI-инварианты: не пропускать panic через границу, проверять NULL и
  UTF-8, освобождать только строки из `rchat_send_json`/
  `rchat_receive_json` через `rchat_free_string`, не логировать пароли и
  токены. Изменение формата запросов/ответов/событий требует повышения
  `API_VERSION`.

## 5. Новое серверное хранилище (`Repo`)

Контракт — `rchat_server::repo::Repo`; сервисный слой (`rchat-server`)
зависит только от него. Требования:

- транзакционные границы совпадают с бизнес-операциями: регистрация
  (пользователь + устройство + предключи + сессия), вставка сообщения вместе
  с получателями и событиями журнала, выдача предключей, применение
  receipts;
- `client_message_id` уникален в рамках чата (идемпотентность отправки);
- журнал синхронизации ведётся на устройство, `seq` непрерывен; хранится
  минимально доступный `seq` (retention → `resync_required`);
- отзыв устройства атомарно запрещает повторный вход с тем же `device_id`
  и исключает его из выдачи бандлов.

Сборка сервера с другим `Repo` (без правки бинарника):

```rust
let server = Server::start(Arc::new(my_repo), config.clone(), Arc::new(hasher)).await?;
// сетевой слой: rchat_server_storage_sqlite::net::{handle_client, ws_config}
```

## 6. Новый криптопровайдер E2E

Контракт — `rchat_core::traits::CryptoProvider`. Порядок расширения:

1. Реализуйте провайдер как отдельный крейт (пример:
   `rchat-crypto-provider` на vodozemac): идентичность устройства,
   публикация предключей, установление сессии, шифрование на каждое
   устройство-получателя, расшифрование, наличие/удаление сессии, `wipe`.
   Для группового режима добавьте `group_encrypt`, `encrypt_group_key`,
   `apply_group_key`, `decrypt_group` и `rotate_group_session` (см.
   приватный конверт ключа `RMGK`: ключ — непрозрачный для ядра payload
   внутри Olm-сообщения, но обязан нести привязку к `chat_id`).
2. Присвойте версию протокола: константы `E2E_VERSION_*` и
   `E2E_PROTOCOL_*` в `rchat-proto`, capability `e2e.<name>`.
3. Сервер не знает о содержимом: он валидирует **покрытие** и рассылает
   ciphertext-ы адресно. Правила разные: в личном чате копии обязаны
   покрывать все неотозванные E2E-устройства участников, в группе
   содержимое общее (`group_ciphertext`), а персональные копии несут только
   ключ (`payload_kind = GROUP_KEY`) тем устройствам, кому он ещё не выдан.
4. Состояние протокола храните в `CryptoStateStore` (`crypto_state`
   хранилища), ключ шифрования pickle-байтов — в `SecretStore`.
5. Тесты — только с реальной библиотекой (не mock): см.
   `crates/rchat-e2e-tests/tests/e2e_olm.rs`, `message_edit_delete.rs` и
   `group_e2e.rs`.

Смена версии E2E — несовместимое изменение: старые устройства не смогут
участвовать, а сервер должен отклонять/исключать несоответствующие
устройства из покрытия.

## 7. Расширение протокола

Правила эволюции схемы — в `docs/protocol.md` §8 и в шапке
`crates/rchat-proto/proto/rchat/v1/common.proto`. Кратко для нового метода:

1. Добавьте `*Request/*Response` в соответствующий `.proto` с новыми
   номерами; для `Request`/`Response` соблюдайте распределение диапазонов
   (10–19 — чаты/сообщения и т. д.).
2. Объявите capability в `rchat-proto::capabilities`; старый сервер вернёт
   `UNSUPPORTED_METHOD` (для неизвестного метода) или отклонит соединение,
   если возможность указана в `required_capabilities`. Клиент должен уметь
   работать и без необязательной возможности.
3. Реализуйте обработчик в `rchat-server::service` и ветку в ядре
   (`rchat-core`); неизвестные ветви `oneof` уже безопасно превращаются в
   `None` на обеих сторонах.
4. Новое событие журнала: добавьте поле в `SyncEvent` — `kind_hint`
   повторяет номер поля; клиенты, не знающие событие, пропускают его с
   продвижением курсора (правило совместимости), при необходимости — новый
   вид `SyncApply` и ветка в `event_to_apply`.
5. Минорная версия протокола — для совместимых дополнений; несовместимые
   изменения — только с новым major.

## 8. Добавление нового слоя/точки расширения

Ищите место «в контрактах»: если подсистема должна подменяться, это трейт
в ядре или серверном слое, а реализация — отдельный крейт. Пример полного
набора для новой платформы UI: трейтов не нужно — достаточно собрать
`Client` с теми же адаптерами (транспорт/хранилище/секреты/крипта) и
подписаться на `UiEvent`. Полная матрица крейтов и зависимостей — в
`docs/architecture.md` §2.
